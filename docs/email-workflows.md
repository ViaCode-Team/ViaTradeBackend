# Email-сценарии и контракт фронтенда

## Хранение и обработка

Постоянное состояние находится в существующей таблице `Users`. Новых таблиц email-сценариев нет. В `EmailWorkStateJson` хранятся ограниченный журнал успешных операций, намерения отправки и прогресс отзыва сессий. В намерении есть только метаданные токена: назначение, аккаунт, операция, версия и срок. Исходных токенов и их хешей в MySQL нет.

Redis содержит отдельные потоки `email:actions` и `email:mail` в базе 2, токены, результаты, лимиты, метаданные повторов и окончательно неуспешные задания. Это отдельная инфраструктура от Telegram. Настройки `Email:RedisDatabase` и `Email:StreamPrefix` должны совпадать у всех экземпляров API.

API хеширует новый пароль BCrypt до публикации. Текущий пароль при смене email проверяется синхронно; задание получает проверенную версию аккаунта и ID действующей сессии. Само изменение выполняет `EmailWorkflowService` через обработчик Redis Streams. Обычный вход, refresh и проверка доступа обращаются к актуальному состоянию MySQL синхронно.

Все изменения email-состояния, занятия адресов и очистка используют `EmailAccountStore`: одну именованную блокировку MySQL на базу, затем транзакцию `READ COMMITTED`. Блокировка сериализует эти короткие транзакции и позволяет проверить уникальность сразу среди текущих, ожидающих и зарезервированных адресов. Этот выбор ограничивает параллелизм изменений аккаунта; для нескольких writable MySQL primary такой протокол не подходит. Другие записи email-полей должны проходить через этот же протокол. `RELEASE_LOCK` выполняется на том же открытом соединении в `finally`, включая отказ и отмену. При ошибке освобождения пул соединения очищается. См. [MySQL locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html).

Транзакция выполняется через execution strategy EF Core с учётом `EnableRetryOnFailure`. Redis и SMTP находятся за её пределами. GUID задания и достигнутый результат сохраняются вместе с изменением пользователя. Повторное получение задания читает этот результат; конкурентные разные ссылки дополнительно проверяют назначение, операцию, срок и версию состояния. См. [EF Core connection resiliency](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency).

После фиксации завершается токен Redis, записывается результат, восстанавливается публикация намерений и подтверждается сообщение. MySQL, Redis и SMTP не являются одной атомарной транзакцией. Отдельная периодическая сверка восстанавливает результаты, публикацию и отзыв сессий после остановки процесса. Сбой SMTP повторяет только письмо.

## Нормализация, сроки и ограничения

Логин и email обрезаются по краям и приводятся через `ToUpperInvariant` для сравнения. В логине запрещён `@`; этот символ выбирает вход по email. Точки, `+`-метки и другие части адреса сохраняются. Правила конкретных провайдеров не применяются. Email должен быть адресом без display name, длиной до 254 символов. Пароль: 8–72 символа, максимум 72 UTF-8 байта из-за ограничения BCrypt.

| Действие | Абсолютный срок |
| --- | --- |
| Подтверждение регистрации | 24 часа с принятия первой операции |
| Подтверждение нового email | 24 часа с принятия операции смены |
| Сброс пароля | 30 минут с принятия первого запроса сброса |
| Возврат старого email | 48 часов с завершения смены в MySQL |
| Хранение неподтверждённого аккаунта | 7 дней с регистрации |

Задержка очереди и повторная отправка действующей операции не меняют её срок. После истечения подтверждения повторный запрос начинает новую операцию. Повторный запрос сброса не изменяет пароль и не подтверждает email. Успех сброса отзывает сессии, отменяет ожидающую смену адреса и прежние регистрационные ссылки. Неподтверждённому аккаунту выдаётся новая регистрационная ссылка. Аварийная ссылка сохраняет действительность после обычного сброса.

Старый адрес занят на весь период возврата. Следующая смена в этот период запрещена. До подтверждения нового адреса текущий адрес продолжает действовать. Повторный `me/emailChange` с тем же ожидающим адресом и текущим паролем отправляет ещё одну ссылку той же операции после cooldown; заменить действующую ожидающую операцию другим адресом нельзя.

Cooldown письма — 5 минут на нормализованный адрес и назначение; регистрация и её resend делят один cooldown. Счётчики общие для экземпляров API. Дополнительные ограничения в `EmailSettings`: IP-запросы в минуту (30), проверки токенов в минуту (10), вход по одному идентификатору за 5 минут (10), авторизованные email-запросы аккаунта за час (30). Превышение возвращает HTTP 429. Общий предел сообщения потока — 100000; при заполнении новые задания не принимаются, необработанные записи не обрезаются.

## API

Все перечисленные POST, кроме входа, возвращают **202 Accepted**, JSON `{ operationId, resultAccessKey, waitUntil }` и `Location: /api/v1/users/operations/{operationId}`. 202 означает принятие задания. Регистрация и подтверждение не устанавливают cookie и не выполняют вход.

| Метод и маршрут | JSON | Доступ |
| --- | --- | --- |
| `POST /api/v1/users` | `{ login, email, password }` | Публичный |
| `POST /api/v1/sessions` | `{ login, password }` | Логин или email; при успехе 204 и cookie |
| `POST /api/v1/users/emailConfirmation` | `{ token }` | Публичный, без пароля |
| `POST /api/v1/users/emailConfirmation/resend` | `{ login }` | Публичный; логин или email |
| `POST /api/v1/users/passwordReset/request` | `{ login }` | Публичный; логин или email |
| `POST /api/v1/users/passwordReset` | `{ token, newPassword }` | Публичный |
| `POST /api/v1/users/me/emailChange` | `{ email, currentPassword }` | Активная сессия |
| `POST /api/v1/users/me/emailChange/confirm` | `{ token }` | Активная сессия того же аккаунта |
| `POST /api/v1/users/emailChangeRecovery` | `{ token, newPassword }` | Публичный |
| `GET /api/v1/users/operations/{operationId}` | Заголовок `X-Operation-Key: resultAccessKey` | Секрет результата; для авторизованных заданий также JWT владельца |

Публичные операции не принимают доверенный `userId`: аккаунт определяется записью проверенного токена. GET страницы или API-маршрута не применяет подтверждение, сброс или возврат. Ссылки содержат 32 случайных байта в hex; запись Redis адресуется SHA-256 fingerprint и имеет TTL.

Результат: `{ status, code, message, clearCookies }`. Статусы `pending`, `succeeded`, `failed`, `completed`, `indeterminate`. Успех регистрации имеет код `registration_pending`: дальше нужно письмо и подтверждение. Результаты хранятся 24 часа. Ожидание ограничено `Email:JobWaitMinutes` (30, максимум 60); просроченное новое применение запрещено. Если инфраструктура не позволяет подтвердить исход транзакции, статус `indeterminate` сообщает неопределённость, а не отсутствие изменения. После восстановления MySQL журнал позволяет уточнить результат. Клиент должен проверить состояние аккаунта перед повтором такой операции.

Запросы сброса и resend всегда имеют один публичный результат `completed/request_received`: «If the account is eligible, an email will be sent». Он подтверждает приём запроса и не раскрывает наличие аккаунта, eligibility, SMTP-ошибку или время внутренней обработки. Этот результат одинаков ещё до обработки очереди.

Для авторизованного результата проверяются секрет и ID владельца из подписанного JWT. Этот endpoint имеет узкое исключение из проверки активной сессии, чтобы получить результат действия, которое само отозвало сессию. Он не предоставляет доступ к аккаунту. Истёкший JWT требует нового входа того же владельца; новая сессия может прочитать результат с прежним секретом. Неверный секрет, другой владелец и отсутствующий результат дают одинаковый 404. Секрет не передаётся в URL. Ответ не кешируется.

После успешного сброса, смены и возврата GET результата удаляет обе cookie через `AuthCookieService`, возвращает `clearCookies: true`. Клиент должен выполнить этот GET с `credentials: include`, очистить состояние интерфейса и показать вход. Фоновый обработчик не удаляет браузерные cookie. При входе и refresh выполняется повторная проверка версии после создания/ротации сессии. Все защищённые запросы сравнивают версию Redis-сессии с MySQL; сбой физического удаления старых сессий не возвращает им доступ. Удаление идёт порциями по 100 с сохранением прогресса.

## Изменения фронтенда

В этом репозитории нет фронтенда. Нужны страницы регистрации с email, ожидания обработки/письма, подтверждения без пароля, сброса, смены адреса и аварийного возврата с обязательным новым паролем. Профиль `GET /api/v1/users/me` содержит `email` и `nextEmailChangeAt`; nullable/прошедшая дата означает отсутствие действующего периода возврата. Начатая смена также ограничивает следующий запрос другим адресом.

Ссылки ведут на `Email:FrontendUrl`:

- `/emailConfirmation#token=...` → POST подтверждения только после действия пользователя.
- `/passwordReset#token=...` → форма нового пароля и отдельный POST.
- `/emailChangeConfirmation#token=...` → вход того же аккаунта, затем отдельный POST.
- `/emailChangeRecovery#token=...` → новый пароль, отдельный POST без входа.

Страница должна прочитать fragment и удалить его через `history.replaceState` **до** аналитики, сторонних ресурсов и логирования. На этих страницах исключить аналитику и сторонние ресурсы, установить `Referrer-Policy: no-referrer`, не запускать POST автоматически при GET/загрузке. Сохранить токен в памяти до явного действия; при необходимости входа не передавать его сторонним redirect URL. См. [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Результат опрашивать примерно раз в 3 секунды с `X-Operation-Key`; не опрашивать без остановки после конечного статуса. Публичные запросы сброса/resend показывают одинаковое сообщение, включая отсутствие аккаунта. Не хранить пароли после отправки.

## Запуск и эксплуатация

Development: API запускается профилем `https` на `https://localhost:7249`; фронтенд и ссылки — `https://localhost:5173`. CORS разрешает этот точный origin с credentials. Cookie остаются `HttpOnly`, `Secure`, `SameSite=Strict`; оба localhost origin имеют одну site. HTTP-профиль не подходит для браузерного входа с Secure cookie. Production: использовать HTTPS и nginx с API и фронтендом на одной site, предпочтительно на одном origin. `Email:AllowedOrigins` задаёт явные дополнительные origins; wildcard запрещён. Cross-site фронтенд не поддерживает текущие Strict cookie.

Обязательные production-настройки через environment/secret store: `Email__FrontendUrl`, `Email__DataProtectionKeyPath`, `Email__SmtpHost`, `Email__SmtpPort`, `Email__FromAddress`, соединения MySQL/Redis и существующие JWT/security secrets. SMTP credentials/TLS задаются `Email__SmtpUsername`, `Email__SmtpPassword`, `Email__SmtpEnableSsl`. Первоначальный локальный приёмник работает без SMTP credentials; его порты доступны только loopback.

`Email__DataProtectionKeyPath` должен указывать на постоянный каталог ключей, доступный всем экземплярам API. Сохранять его вместе с резервными копиями; права доступа ограничить сервисным пользователем. Указание файлового каталога не шифрует ключи на диске: защитить хранилище средствами развёртывания. Не удалять старые ключи, пока есть защищённые Redis-записи. При потере ключей payload не расшифровывается и попадает в защищённое хранилище отказов. См. [Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0).

Redis нужен версии 6.2 или выше; использованы consumer groups, `XREADGROUP`, `XAUTOCLAIM`, `XACK`. Версия проверяется по информации подключённого сервера без требования admin-команд. Зависшие сообщения доступны другим уникальным consumers через 60 секунд; lease действует 120 секунд, обработка ограничена 30 секундами. Повторы: 5, 10, 20… секунд, максимум 300 секунд, 8 попыток по умолчанию. Account, mail и maintenance работают независимыми циклами. Окончательные ошибки хранятся отдельно защищёнными ключами `email:dead:*` с TTL 7 дней. Потоки удаляют только завершённые сообщения. См. [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/), [XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/), [XACK](https://redis.io/docs/latest/commands/xack/).

SMTP-статус называется `acceptedByTransport`, а не «доставлено в почтовый ящик». До истечения срока повторяется та же ссылка; просроченное или уже отменённое письмо не отправляется. Если транспорт принял письмо, а процесс остановился до записи исхода, повтор возможен. Ровно одно письмо не гарантируется.

`deploy/email-services.compose.yaml` предоставляет локальный Mailpit, Redis primary и replica с постоянными томами; Redis вынесен на порт 6380, чтобы не менять уже запущенный сервер 6379. `deploy/redis-email.conf` включает AOF с `appendfsync always`, RDB и `noeviction`. Primary запрещает записи без достаточно актуальной replica. Перед запуском задать `VIATRADE_REDIS_TAG` (одобренный pinned release, тесты выполнялись на 8.0.0) и `VIATRADE_REDIS_PASSWORD` из secret store. Выполнить:

```powershell
docker compose -f deploy/email-services.compose.yaml up -d
```

Для одного Mailpit достаточно `docker compose -f deploy/email-services.compose.yaml up -d mailpit`. Его UI: `http://localhost:8025`, SMTP: `localhost:1025`; значения уже есть в Development-конфигурации. Использован документированный стабильный тег; см. [Mailpit Docker](https://mailpit.axllent.org/docs/install/docker/). Для compose Redis указать отдельное соединение `localhost:6380,password=...` через secrets/environment, не сохранять пароль в shared configuration. Не переключать живую систему на пустой Redis до остановки приёма и обработки старых очередей.

Резервировать **Redis volumes, MySQL и каталог Data Protection вместе**. Для согласованной копии Redis дождаться успешного `BGSAVE`, сохранить RDB и AOF manifest/segments целиком; архивировать вне хоста, ограничить доступ и проверять восстановление на отдельной инстанции. Например, внутри контейнера с уже заданным secret: `REDISCLI_AUTH="$VIATRADE_REDIS_PASSWORD" redis-cli BGSAVE`, затем проверить `INFO persistence`/`LASTSAVE` перед копированием. В расписании инфраструктуры нужны регулярные off-host backups и контроль AOF/RDB ошибок. Compose replica находится на том же Docker-хосте и не защищает от его потери; production replica и backups должны находиться в другом failure domain. Автоматический failover этим compose не настраивается. См. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Streams сами по себе не исключают потери данных. При потере Redis теряются сессии, секреты результатов и ещё не применённые задания: API не сообщает их как успешно выполненные; пользователям нужен повторный вход/запрос. Неотправленные намерения MySQL восстанавливаются с прежним абсолютным сроком, выпуск может дать новую ссылку. Уже завершённые отправки очищаются; ранее отправленные ссылки, чьи Redis-записи потеряны, отклоняются. Для регистрационного подтверждения/сброса можно запросить новое письмо, для утратившегося аварийного токена требуется восстановление Redis из резервной копии в пределах срока. Ни обычный reset, ни потеря Redis не снимают MySQL-резервацию прежнего адреса раньше срока.

Переход согласован для отсутствующих/удалённых до развёртывания старых аккаунтов. Миграция не удаляет аккаунты, не придумывает email и не подтверждает отсутствующие адреса. Обнаруженные старые аккаунты с nullable email/normalized login требуют отдельной процедуры до запуска; обычный вход для них не разрешён.

## Воспроизводимые проверки

```powershell
dotnet tool restore
dotnet build ViaTradeBackend.sln
dotnet test Tests/ViaTrade.Tests.csproj --no-build
```

Email integration tests используют настоящий MySQL и Redis, создают только изолированную временную базу с коротким GUID-именем, собственные Redis prefixes и удаляют свои данные. У соединения MySQL должны быть права создать/удалить тестовую базу. Источники: `VIATRADE_TEST_MYSQL` / `VIATRADE_TEST_REDIS`, иначе Development JSON и User Secrets API. Redis DB 15 используется с уникальными prefixes; пользовательские/session keys создаются с отдельными user IDs и очищаются адресно, `FLUSHDB` не используется.

Проверки охватывают миграции, регистрацию/подтверждение, login/email, конкурентные ссылки/адреса, цели/сроки токенов, отказ до и после commit, восстановление результатов и намерений, сохранение recovery после reset, гонки login/refresh, bounded отзыв сессий, очистку, shared limits, PEL reclaim/lease, повторы/dead letters, persistent Data Protection, HTTP API с двумя workers и настоящий loopback SMTP-приёмник.

Инъекции ошибок моделируют остановки вокруг commit и Redis completion; тесты не завершают реальный процесс через kill. Docker compose, production failover, off-host backup/restore, реальные браузерные страницы и доставка в реальный почтовый ящик требуют отдельной проверки развёртывания.
