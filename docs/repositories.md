# Repositories and specifications

Application handlers use `IReadRepository<TEntity>` for reads and `IRepository<TEntity>` for writes. Both are registered as open generics backed by the scoped `AppDbContext`. Simple filters and projections use expression overloads directly; they do not require separate specification classes.

Specifications live in `Application/<Feature>/<Operation>` (or `<Feature>/Common` when reused) and use Ardalis.Specification 9.3.1. They encapsulate filters, navigation includes, ordering, and bounded batches. Handlers pass result projection expressions directly at the query call site. `PageSpecification` stores only page metadata alongside the inherited filtering and ordering logic. `OrderedSpecification` builds one `OrderBy` followed by `ThenBy` clauses. Page specifications append the entity ID for stable ordering. Related strategy specifications inherit the user ownership filter from `UserStrategyLinksSpecification`. Search criteria apply independently of exact filters.

`IReadRepository<TEntity>.GetPageAsync` returns a `PageResult<TResult>` from a page specification and a projection expression. An overload without a projection returns a page of entities for internal use. `EfRepository<TEntity>` inherits both methods from `ReadEfRepository<TEntity>`. Handlers pass `PageOptions` only to specification constructors, which snapshot the page number, size, and offset. The repository applies the specification to the EF query, then adds `Skip`, `Take`, and `Select` without mutating the specification or creating another one. The first page requests one extra item to detect whether COUNT is needed; the extra item is removed before returning the result. A first page that fits needs one SELECT; an overflowing first page also executes COUNT. Later pages execute COUNT first and skip the data SELECT when the offset is at or beyond the total. Exact instrument symbols and strategy names follow the same pagination rules, preserving the actual total on empty later pages. Cancelled page queries send no SQL. Database calls execute sequentially on the scoped context. Specifications do not validate inputs; FluentValidation handler decorators validate commands and queries before execution; API model binding still handles malformed HTTP input.

`PageResult<T>.FromList` builds a page from an already ordered in-memory collection and explicit page number and size, rejecting non-positive bounds. Signal handlers use it after collecting file data; session handlers use it after `ISessionRepository.ListByUserAsync` loads existing sessions. Handlers use request properties directly instead of making local copies. They do not create database specifications for in-memory pagination.

Database reads follow the globally configured `NoTracking` behavior. Add/remove operations are staged until `IUnitOfWork.SaveChangesAsync` or repository `SaveChangesAsync`. To save changes to a detached entity, call repository `Update` explicitly first. `GetByIdAsync` queries through EF and respects global filters; user-owned data must use a predicate or specification containing `UserId` together with the requested ID. Instruments and strategies are shared reference data.

Specialized repositories have independent interfaces and do not inherit the generic repository. They retain only operations that need SQL aggregation, queries across independent entity sets, or typed atomic updates:

- `INoteRepository`: aggregate counts and update note text.
- `IReminderRepository`: conditionally update, publish, or confirm delivery.
- `IStrategyRepository`: statistics and strategy/instrument link state across entity sets.
- `ITradeRepository`: statistics, chart buckets, date range, and update trade fields.
- `IUserRepository`: update Telegram ID and last login time.

Deletes use generic `ExecuteDeleteAsync` with a predicate or specification. Updates retain EF `ExecuteUpdateAsync` internally rather than loading entities, and return affected row counts for handlers to evaluate. These operations execute immediately without `SaveChangesAsync` and do not synchronize tracked entities. Each call is a separate SQL statement; a workflow requiring multiple statements to commit together needs an explicit transaction. See [EF Core bulk operations](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete).

User-facing bulk operations include ownership predicates. Publishing a reminder also carries its user ID. Delivered-reminder cleanup and due-reminder batches intentionally span users as background maintenance operations.

Redis caches use `ICacheRepository<TEntity>` backed by `BaseRedisRepository<TEntity>`. Telegram tokens use the generic cache directly, including atomic `ConsumeAsync` implemented with Redis GETDEL. Session storage keeps its dedicated repository because its Lua scripts, indexes, rotation, and expiry handling cannot be represented by ordinary cache operations.

Operations use local CQRS contracts without a mediator: `IQuery<TResult>`, `ICommand`, `ICommand<TResult>`, and their `HandleAsync` handler interfaces live in `Application/Common/Abstractions`. Each feature contains operation folders such as `Notes/Get` and `Notes/UpsertInstrument`; request records, handlers, and operation-specific specifications, filters, and result records live together. Shared feature types belong in `<Feature>/Common`; types reused across features belong in `Application/Common`. FluentValidation validators live beside their command, query, or shared input model. Shared input validators hold field rules once and are composed by operation validators. Scoped handler decorators invoke ValidateAsync before the handler and translate failures into the application ValidationException, returned as HTTP 400 with field errors by the existing middleware.

Query handlers project database rows into result records named with the `Result` suffix. They do not return EF entities. Commands return result records when needed. Mutable Redis session storage uses `Auth/Common/SessionData`, while the sessions query returns separate `SessionResult` records. A token-consuming operation is a command because it modifies cache state.

Database result records expose reusable `Projection` expressions, which handlers pass directly to repository methods. Related-entity queries use `LinkProjection`; due reminders use `DueReminderResult.Projection` to include the Telegram recipient. Public `ReminderResult` contains only the public reminder fields; delivery results retain the recipient for the publisher but exclude it from JSON. Subscription projections accept the user ID as a scalar parameter. No result factories or separate projection classes are required, and expressions are not compiled before passing them to EF. Conditional operators are allowed only within projections to handle nullable navigation properties. `NoteResult.Projection` returns null for absent or filtered related entities. Session results use a delegate projection because their source is already in memory. Query and command handlers access request properties directly instead of copying them into local variables.

Controllers receive the matching handler through an action's `[FromServices]` parameter and call `HandleAsync` with the completed command or query. Controllers bind Application commands with flat payload fields from the body and queries with grouped filters from the query string, add route IDs and the authenticated user ID, and return Application result records directly. There are no separate API request/response records or API mapper. Login, registration, trade, note, reminder, and subscription commands contain their payload fields directly; their command validators enforce the field rules without separate Input models. Session queries also receive the current session ID to set IsCurrent. Routes, HTTP methods, pagination, and authorization remain unchanged. Command bodies use flat JSON fields as documented in `body-binding.md`. Background tasks resolve the same handler contracts inside their existing scopes. `AddApplicationLayer` uses Scrutor 7.0.0 to scan only the Application assembly in one selection for `IQueryHandler<,>`, `ICommandHandler<>`, and `ICommandHandler<,>`. It registers only concrete handler interfaces as scoped, including non-public implementations, scans validators, and decorates the three handler interface shapes with validation. Open generic decorator types are excluded from handler discovery. New handlers are discovered automatically; duplicate handler contracts cause registration to fail. Regression tests check registration coverage, scope resolution, and duplicate rejection.

Run `dotnet build` and `dotnet test Tests/Tests.csproj`. Regression tests execute against SQLite in memory with the application EF model, and separately check SQL translation with the production Pomelo MySQL provider. They do not execute against a live MySQL or Redis server.
