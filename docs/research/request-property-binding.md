# ASP.NET Core request property binding research

## Findings

The framework does not provide a built-in action-parameter attribute that splits one JSON body across selected properties while binding other properties of the same object from route, query, or headers. ASP.NET Core treats `[FromBody]` as a request to give the complete body to an input formatter. Property-level binding-source attributes on that body model are ignored, and an action must not have multiple body-bound parameters because the request stream is consumed once. The supported built-in shape is separate action parameters for each source, or one body model plus separate route/query/header parameters. [ASP.NET Core model-binding docs](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/model-binding?view=aspnetcore-10.0)

The maintainers confirmed this is by design: the formatter deserializes the body as one payload and MVC does not break JSON into key-value pairs for further property binding. They specifically said there are no plans to add flat mixed-source binding, citing the cost of turning larger JSON bodies into value pairs. A custom binder can implement other behavior, but it is custom deserialization logic rather than the standard MVC pipeline. [dotnet/aspnetcore #48391](https://github.com/dotnet/aspnetcore/issues/48391)

The built-in `[Bind]` and `[BindNever]` attributes do not exclude properties from JSON body deserialization: they affect form/value-provider model binding, not input formatters. `[JsonIgnore]` is a serializer-contract attribute on a property, so it applies wherever that CLR type is serialized or deserialized; it does not express “ignore this property for this action only.” Starting with .NET 7, System.Text.Json supports contract customization via `JsonTypeInfo` resolvers/modifiers, including removing properties from a contract. That is a serializer customization point, not a built-in per-action MVC binding attribute; any endpoint-specific use must ensure the MVC formatter uses the appropriate options and the API description exposes the same shape. [MVC docs on `[Bind]`](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/model-binding?view=aspnetcore-10.0#bind-attribute), [System.Text.Json custom contracts](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/custom-contracts), [`JsonIgnoreAttribute`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.serialization.jsonignoreattribute?view=net-10.0)

OpenAPI is a separate contract projection. ASP.NET Core's `ApiExplorer` describes each input with its binding source, type, and model metadata. Swashbuckle builds operations from `ApiDescription`, generates schemas from model types, and provides operation/schema filters for deliberate edits. Therefore, changing only deserialization does not guarantee an accurate OpenAPI body schema; a custom input formatter or serializer contract needs a corresponding API-description/schema rule. Conversely, changing only the OpenAPI schema does not alter runtime binding. [ApiParameterDescription](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.mvc.apiexplorer.apiparameterdescription), [Swashbuckle generator and filters](https://github.com/domaindrivendev/Swashbuckle.AspNetCore/blob/master/docs/configure-and-customize-swaggergen.md)

## Community evidence of the problem

These are examples of recurring user pain, not authorities for framework behavior:

- In [dotnet/aspnetcore #48391](https://github.com/dotnet/aspnetcore/issues/48391), the author asks for a single flat request model combining body, path, query, header, and custom-bound properties, and for `ApiExplorer`/Swagger to honor those property attributes. The issue was closed as “By Design”; maintainers explained the formatter boundary and said the feature was not planned.
- In [dotnet/aspnetcore #45392](https://github.com/dotnet/aspnetcore/issues/45392), a user reports that `[FromRoute]` on a property of a body-bound model is still read from JSON, can trigger required-property validation, and remains in the Swagger body schema. The report used .NET 6/7. GitHub currently shows the issue as closed, but the issue page does not record a fix or resolution, so it is evidence of the reported problem rather than proof of current .NET 10 behavior.
- [Swashbuckle #2315](https://github.com/domaindrivendev/Swashbuckle.AspNetCore/issues/2315) shows a custom binder that merges route values into a JSON model and a Swagger UI interaction that leaves the custom code without the body it expected. The issue has no documented resolution. It reinforces that a working custom binder does not automatically make ApiExplorer/Swagger describe or invoke it correctly.
- [Swashbuckle #1723](https://github.com/domaindrivendev/Swashbuckle.AspNetCore/issues/1723) asks how to keep a shared request/response type while hiding an inherited correlation ID from a DELETE request schema and mapping the route ID into the request. The author tried `[JsonIgnore]` and `[FromRoute]` but could not get the intended per-operation contract.
- [dotnet/AspNetCore.Docs #11699](https://github.com/dotnet/AspNetCore.Docs/issues/11699) reports that a complex type's body property is populated while its header property remains null, and demonstrates separate body/header types as the working shape. This report is from ASP.NET Core 2.2; current documentation independently states the same input-formatter rule.
- [Stack Overflow: “How to utilize FromBody and FromRoute in the same model with model binding”](https://stackoverflow.com/questions/78445766/how-to-utilize-frombody-and-fromroute-in-the-same-model-with-model-binding) asks to take one DTO property from route and the rest from JSON. The answers/comments illustrate the same confusion around source attributes on body models.
- [Stack Overflow: “Is it possible to combine [FromRoute] and [FromBody] in ASP.NET Core?”](https://stackoverflow.com/questions/51316269/is-it-possible-to-combine-fromroute-and-frombody-in-asp-net-core) asks to combine route/query/body into one model, including for unified validation. One commenter describes manually copying route values into the model in the controller.

Searches for the exact names `FromRouteProperties` and `IgnoreProperties` did not surface established ASP.NET Core framework attributes; they appear to describe application-specific behavior. The related framework-level questions use the built-in `[FromRoute]`, `[FromBody]`, and `[JsonIgnore]` names instead.

## Implications for this repository

The repository's `FromRouteProperties` / related attributes and `IgnoreProperties` solve a real gap between a stable application command/query type and an action-specific HTTP contract. Their custom value is selecting properties per action, reading them from mixed sources, excluding values before JSON deserialization/validation, and projecting the same selection into OpenAPI. No single stock MVC or System.Text.Json attribute covers all of those behaviors.

The minimal built-in alternative is to expose separate source parameters (for example, `[FromRoute] int tradeId` and `[FromBody] UpdateTradeBody`) and construct the unchanged command in the action. This gives MVC and OpenAPI an explicit source/type for each input, but requires a body type that exactly models the JSON shape. A generator such as Facet can reduce the handwritten body-type properties, but still generates a distinct type and does not remove the mapping step.

If keeping the existing command/query as the action parameter is a requirement, a custom action-specific binding layer remains necessary for exact mixed-source binding and body exclusion. The safest simplification target is internal implementation: use MVC's existing scalar/file binders and validation metadata where possible, keep action-level property selection as the one source of truth, and make OpenAPI projection consume that same metadata. System.Text.Json contract modifiers can replace some JSON property-filter code only if the selected per-action contract is also selected by the MVC input formatter and faithfully reflected in OpenAPI; the framework does not wire those pieces together automatically.
